## Domain Language

**Cart**:
A collection of cart items a customer intends to purchase, stored client-side via Zustand persist.
_Avoid_: Basket, bag

**Cart Item**:
A single product line with an id, productType, label, image, price, and quantity. Same id = same line; adding again increments quantity.

**Magnet**:
A product from the magnets collection with selectable variants (Kedarnath, Dwarka, Puri, Rameshwaram, Pack of 4). Each variant is a separate cart item.

**Poster**:
A product from the posters collection. Currently a single SKU without variants (Kedarnath edition).

**Customer**:
An authenticated user who can proceed to checkout. Auth is handled by better-auth.

### Relationships

- A **Cart** contains zero or more **Cart Items**
- A **Cart Item** belongs to exactly one product type (**Magnet** or **Poster**)
- A **Magnet** has multiple **Variants**; each variant produces a separate **Cart Item**
- A **Poster** has no variants; adding it always produces the same **Cart Item**

### Example dialogue

> **Dev:** "When the customer clicks BUY NOW on a magnet variant, do we add to cart first or go straight to checkout?"
> **Domain expert:** "BUY NOW adds to cart then redirects to checkout — but only if the customer is signed in. Otherwise it sends them to sign-in first."

### Flagged ambiguities

- "BUY NOW" acts as "add to cart + redirect to checkout". Not a separate express-purchase flow.
- "Proceed to Checkout" on the cart page is a placeholder — payment integration is not yet wired.

## Architecture

### Auth
- **Library**: better-auth `^1.6` (Drizzle adapter, PostgreSQL)
- **Methods**: Email/password + Google OAuth
- **Server instance**: `src/lib/db/auth.ts`
- **Browser client**: `src/lib/db/auth-client.ts`
- **Auth routes**: `/api/auth/[...all]` (catch-all)
- **User session**: server-prefetched in `layout.tsx`, passed to `AuthProvider`
  (`src/components/providers/auth-provider.tsx`) which hydrates the client — no first-paint flash
- **Hook**: `useSession()` returns `{ data, isPending }`
- **Cookie cache**: enabled (`maxAge` 5 min) — most session checks read the signed cookie, not the DB

#### better-auth workflow (READ before touching auth — it's a 3rd-party lib)

> **Official docs are vendored at `docs/agents/better-auth/better_auth_official.md`.** Read that
> before changing anything auth-related — do not rely on model memory of the library.

**Schema type — GENERATED by better-auth, NOT hand-written.**
- better-auth has a **strict schema** and only works against **its own generated tables**. The
  four auth tables in `src/lib/db/schema.ts` — `user`, `session`, `account`, `verification` — are
  produced by the better-auth CLI (`npx @better-auth/cli generate`), then pushed with
  `npx drizzle-kit push`. Do not author or restructure these tables by hand.
- The generated shape is the **contract better-auth enforces** — it reads/writes them through the
  Drizzle adapter (`drizzleAdapter(db, { provider: "pg", schema })` in `auth.ts`). Renaming a
  column, dropping a field, or diverging from the generated model silently breaks login.
- To add a feature that needs new columns (2FA, orgs, extra `user` fields): enable the option/
  plugin in `auth.ts` **first**, then **re-run `npx @better-auth/cli generate`** to regenerate the
  schema, then `npx drizzle-kit push`. Never patch the tables ahead of the generator.
- Reference columns (for reading, not editing): `session.token` (unique, the value signed into the
  cookie), `session.expiresAt`, `session.userId` (FK → `user.id`, cascade). `account.password`
  holds the email/password hash; OAuth rows store `providerId` + tokens instead.

**How cookies are fetched.**
- On sign-in better-auth sets a signed, httpOnly session cookie (`better-auth.session_token`,
  signed with `BETTER_AUTH_SECRET` from `src/env.ts`). It maps to `session.token` in the DB.
- **Server** (RSC, route handlers, server actions): read via
  `auth.api.getSession({ headers: await headers() })` — `headers()` from `next/headers` forwards
  the request cookies. Canonical example: `src/app/admin/page.tsx`. This is the ONLY correct
  server-side way to read the session; don't parse the cookie by hand.
- **Server prefetch → client hydration**: `layout.tsx` (async) calls `getSession` once, maps it to
  the `SessionData` shape, and passes it to `<AuthProvider initialSession={...}>`. The provider
  uses it as the fallback while the client `useSession()` is still pending and reports
  `isPending: false` when it's present, so signed-in UI renders on first paint with no round trip
  and no flash. `headers()` opts the app into dynamic rendering (expected for an auth-driven app).
- **Client**: `authClient.useSession()` (better-auth react hook) → GETs `/api/auth/get-session`,
  which the catch-all route serves; it revalidates in the background and takes over once resolved.
  `AuthProvider` wraps this hook and re-exports a trimmed `{ data: { user, session }, isPending }`
  via context; components call the local `useSession()` from `auth-provider.tsx`, not the raw
  client hook.
- The catch-all `src/app/api/auth/[...all]/route.ts` is just
  `toNextJsHandler(auth)` — it serves every better-auth endpoint (sign-in, sign-out,
  get-session, OAuth callbacks). Leave it as-is.

**Touch / don't-touch.**
- ✅ Touch: `auth.ts` (config: providers, `session`, plugins), `auth-client.ts` (client plugins /
  baseURL), `auth-provider.tsx` (context shape — keep `data?.user` / `isPending` contract; 4
  consumers rely on it: `Navbar`, `CartComponent`, `MagnetsComponent`, `PostersComponent`).
- ⚙️ Regenerate, don't hand-edit: auth tables in `schema.ts` are CLI-generated —
  `npx @better-auth/cli generate` then `npx drizzle-kit push`. Change `auth.ts` config first,
  regenerate second.
- ⛔ Don't touch: the generated auth tables by hand, `[...all]/route.ts` (the catch-all handler),
  manual cookie parsing/signing (`BETTER_AUTH_SECRET` handles it), or bypassing `getSession` to
  query the `session` table directly for auth decisions.
- 🔐 Cookie-cache caveat (enabled, `maxAge` 5 min in `auth.ts`): cached sessions can be stale up
  to `maxAge`. Security gates already opt out via `query: { disableCookieCache: true }` —
  `src/app/admin/page.tsx` and `src/app/api/admin/orders/route.ts`. Add the same to any new
  revocation-sensitive check.

### Cart

- **File**: `src/lib/cart-store.ts`

- **Important**: Cart is purely localStorage, not synced to DB

### Payments (Razorpay)
- **Library**: razorpay `^2.x` (server SDK), checkout.js (client-side modal)
- **Server instance**: `src/lib/razorpay.ts`
- **Status**: Test mode (placeholder keys `rzp_test_*`) — switch to live keys before real transactions
- **Env vars**: `RAZORPAY_KEY_ID` / `RAZORPAY_KEY_SECRET` (server), `NEXT_PUBLIC_RAZORPAY_KEY_ID` (client fallback)
- **Monetary amounts**: stored in **paise** (integer) everywhere — DB, Razorpay API, API responses
- **Order tables**: `orders` (shipping + status) + `order_items` (line items) in `src/lib/db/schema.ts`
- **Order queries**: `src/lib/order-queries.ts` — left-join orders+items into `OrderWithItems[]`

#### Payment flow — step by step

**1. Client initiates checkout** (`src/app/cart/CartComponent.tsx:30-130`)
- User clicks "Proceed to Checkout" → `handleCheckout()` fires
- Session check: if not authenticated, redirect to `/sign-in`
- Fetch user's default address via server action (`getUserAddresses()`)
- POST `{ items, addressId }` to `/api/checkout`

**2. Server creates order + Razorpay order** (`src/app/api/checkout/route.ts`)
- Authenticate: `auth.api.getSession()` — 401 if no session
- Rate limit: Arcjet sliding window 10 req/60s (DRY_RUN)
- Validate body: items array non-empty, address exists in DB
- Calculate `totalAmount = Σ(price × quantity)` in rupees, convert to paise (`× 100`)
- Insert into `orders` table: `id: ord_${nanoid(16)}`, `userId`, `paymentStatus: "pending"`, `deliveryStatus: "processing"`, shipping copy from address
- Insert into `order_items` table: one row per item with `id: oi_${nanoid(16)}`, `orderId`, `productType`, `label`, `image`, `price`, `quantity`
- Call `razorpay.orders.create({ amount, currency: "INR", receipt: orderId })`
- Update `orders` row with `razorpayOrderId` from Razorpay response
- Return `{ orderId, razorpayOrderId, amount, key_id }`

**3. Client opens Razorpay checkout modal** (`CartComponent.tsx:64-123`)
- Dynamically inject `<script src="https://checkout.razorpay.com/v1/checkout.js">` (sets `razorpayLoadedRef` so it runs once)
- Construct `Razorpay(options)` with: `key` from API response, `amount`, `order_id`, `name: "Tripper.ai"`, `theme.color: "#f48b29"`
- Register `handler` callback (fires on successful payment)
- Register `payment.failed` event handler
- Register `modal.ondismiss` for user-cancelled
- Show overlay with spinner + warning text ("do not go back or refresh")
- Call `rzp.open()` to display Razorpay iframe

**4. Client verifies payment** (`CartComponent.tsx:83-103` → `/api/verify-payment`)
- Razorpay modal calls `handler` with `{ razorpay_payment_id, razorpay_order_id, razorpay_signature }`
- Client POSTs `{ orderId, razorpayPaymentId, razorpayOrderId, razorpaySignature }` to `/api/verify-payment`
- Server recomputes HMAC-SHA256: `crypto.createHmac("sha256", RAZORPAY_KEY_SECRET).update(\`${razorpayOrderId}|${razorpayPaymentId}\`).digest("hex")`
- Compare against `razorpaySignature` — 400 if mismatch
- On match: update `orders` → `paymentStatus: "completed"`, store `razorpayPaymentId`
- Return `{ success: true }`
- Client clears cart (`clearCart()`), redirects to `/order/${orderId}`

**5. Webhook (idempotent backup)** (`src/app/api/webhooks/razorpay/route.ts`)
- Razorpay sends `payment.captured` event to `/api/webhooks/razorpay`
- Verify webhook signature: HMAC-SHA256 of raw request body against `x-razorpay-signature` header — 401 if mismatch
- No session check (webhook is server-to-server, no user cookie)
- Arcjet shield only (no rate limit rule — Razorpay retries are expected)
- Parse event body: `payload.payment.entity.order_id` → find `orders` by `razorpayOrderId`
- Update `paymentStatus: "completed"`, store `razorpayPaymentId`
- Return `{ received: true }` (Razorpay expects 200)
- Note: both verify-payment AND webhook can fire for the same order — harmless since both SET the same status

**6. User views orders** (`src/app/api/orders/route.ts` → `src/lib/order-queries.ts`)
- GET `/api/orders` — authenticated, rate limited 30 req/60s
- `getOrdersWithItems(userId)` — left-join orders + order_items, grouped via `Map` in `groupOrderRows()`
- Returns `OrderWithItems[]` shape: order fields + `items[]` array
- Individual order: `GET /api/order/[id]` → `getOrderById(id, userId)` (scaffolded at `src/app/order/[id]/page.tsx`)

#### Order statuses

| Field | Values | Set by |
|-------|--------|--------|
| `paymentStatus` | `pending` → `completed` | verify-payment OR webhook |
| `deliveryStatus` | `processing` → `shipped` → `delivered` / `cancelled` | Admin PATCH `/api/admin/orders` |

No `failed`/`refunded` payment tracking yet — payment failures surface as client-side toast errors, but the order stays `pending` in DB.

#### Touch / don't-touch

- ✅ **Touch**: `CartComponent.tsx` (checkout button, Razorpay options, success/error handlers), `checkout/route.ts` (order creation logic, pricing), `verify-payment/route.ts` (signature verification), `webhooks/razorpay/route.ts` (event handling), `razorpay.ts` (SDK config)
- ⚙️ **Regenerate after schema changes**: `schema.ts` (orders/order_items columns — hand-written table, not auto-generated like auth)
- ❌ **Do not store amounts as floats** — always paise integers
- ❌ **Do not expose `RAZORPAY_KEY_SECRET` to client** — only `key_id` is public; the secret stays server-side for HMAC verification
- ❌ **Do not skip webhook signature verification** — without it, anyone can POST fake `payment.captured` events
- ⚠️ **Race condition**: both verify-payment and webhook can fire. Idempotent (both SET `paymentStatus`), but avoid double-charge logic if adding email/SMS notifications later

#### Razorpay key env vars pattern

Using **two separate vars** (not a single shared one):
```
RAZORPAY_KEY_ID          → server SDK (razorpay.ts)
RAZORPAY_KEY_SECRET      → server SDK + HMAC secret (verify-payment, webhooks)
NEXT_PUBLIC_RAZORPAY_KEY_ID → exposed to client, but NOTE: client uses `key_id` from API response, not from env
```

The checkout API returns `key_id` in the response body so the client never reads `NEXT_PUBLIC_RAZORPAY_KEY_ID` directly. This lets the server control which key is active without a client rebuild.

## Key Conventions

### ID Pattern
```
prefix_nanoid(16)
```
- `ord_` — orders
- `oi_` — order items
- `addr_` — addresses (note: using `nanoid(16)` in code, not explicitly `addr_` prefix)
- `int_` — interest emails

### Naming
- Use `kebab-case` for file names (Next.js convention)
- Use `PascalCase` for React components
- Use `camelCase` for functions, variables, hooks
- Use `UPPER_SNAKE_CASE` for constants/enums

### Styling
- **Tailwind CSS v4** with `@tailwindcss/postcss`
- **shadcn/ui** radix-nova style components
- **Icons**: `lucide-react` only
- **Fonts**:
  - `var(--font-cinzel)` — headings, brand text
  - `var(--font-inter)` — body text
  - `var(--font-playfair)` — accent text
  - `var(--font-instrument-serif)` — display/serif headings
- **Theme**: Dark (#0a0a0a bg, #f48b29 accent, #1a1c1c surface)
- Use `cn()` utility from `src/lib/utils.ts` for conditional classes

### Data Flow
1. **Cart**: Client-side only (localStorage). Never read by server.
2. **Checkout**: Client sends `{ items, addressId }` to `/api/checkout` — see [Payment flow](#payment-flow--step-by-step) above for full 6-step walkthrough.
3. **Payment**: Razorpay checkout.js modal → client gets `razorpayPaymentId` → POST to `/api/verify-payment`
4. **Webhook**: Razorpay sends `payment.captured` → server updates order status

### Address Validation
- State must be from `INDIAN_STATES` enum in `src/lib/validation/india-geo.ts`
- Pincode-to-state lookup via `PINCODE_RANGES` in `src/data/pincode-ranges.ts` (auto-generated, do not edit)
- Phone validation: 10 digits

## Important Rules

1. **Never write `npm run lint` or `npm run test`** — they don't exist.
2. **Run migrations manually**: `npx drizzle-kit push` (no package.json script).
3. **Arcjet is DRY_RUN** — rate limits logged but not enforced. Change to `LIVE` when needed.
4. **Cart is localStorage only** — no server sync. Clearing browser storage loses cart.
5. **All monetary values in paise** — multiply by 100 when sending to Razorpay, store as integer in DB.
6. **ADMIN_EMAILS env var** — comma-separated emails. Must be set for `/admin` access.
7. **Razorpay test mode** — using test keys. Switch to live keys and update webhook URL before real transactions.
8. **No CMS** — product data is hardcoded in components. Adding products requires code changes.
9. **Don't delete `src/data/pincode-ranges.ts`** — it's auto-generated and the pincode lookup depends on it.
